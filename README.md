# Meterya App

Meterya App is the Flutter web interface for household energy data. It uses the Meterya API for calculations and storage and Keycloak for sign-in. The browser communicates with all three services through one HTTPS origin.

## Features

- Workspaces, members, roles, and metering points
- Readings, tariffs, consumption, cost views, and monthly billing
- Reading photos, virtual meters, meter transitions, and heat pump views
- Audit history, reports, and operator backup and restore
- Responsive layout with system, light, and dark appearance modes

## Use with Docker Compose

The app image is publicly available from GHCR. No GitHub account, access token, or registry login is required to pull it. Use the `latest` tag in your deployment's Compose file:

```yaml
services:
  web:
    image: ghcr.io/roman-kiefer/meterya-app:latest
    restart: unless-stopped
```

The HTTPS proxy should send `/api/*`, `/auth/*`, and `/health/*` to the API, `/identity/*` to Keycloak, and other paths to `web:8080`. The web image serves Flutter routes such as `/profile` and `/invitations/accept` through its `index.html` fallback. Keep the browser, API, and Keycloak on the same public HTTPS origin so server-side authentication cookies work. Do not expose the web container directly to the internet.

The snippet above defines only the web service. Your complete deployment also needs the API, Keycloak, PostgreSQL, and the proxy routing described above. If the public HTTPS proxy runs on the host, publish the Compose gateway only on loopback, for example `127.0.0.1:8080:8080`.

Once the full Compose configuration is in place, pull and start the services:

```sh
docker compose pull
docker compose up -d
docker compose ps
```

## Languages

The app supports German and English. Flutter selects the language from the
browser/system language preferences, including regional variants such as
`de-DE`, `en-US` and `en-GB`. English is the fallback when none of the preferred
languages is supported. There is currently no manual language selector.

`lib/l10n/app_de.arb` is the template; `lib/l10n/app_en.arb` contains the English
translations. Add new messages to both files, keeping placeholder names and ICU
select keys identical. Run `flutter gen-l10n` after changes. The generated
`app_localizations*.dart` files are ignored by Git and are also regenerated by
Flutter builds. Widgets use `AppLocalizations.of(context)`; date and decimal
formatting and HTML reports use the resolved language. Amounts remain in euros,
and date inputs and API data retain ISO dates (`YYYY-MM-DD`). Decimal inputs
accept either a dot or a comma.

## Development checks

Use a Flutter SDK compatible with the Dart constraint in `pubspec.yaml`. The release workflow uses Flutter `3.47.4`.

```sh
flutter pub get
flutter analyze
flutter test
flutter build web
```

The compiled files are in `build/web/`. They are generated and are not committed. The app uses relative API paths and needs the proxy routes above for an end-to-end sign-in flow.

The sign-in page and navigation footer show the running UI and API versions
independently. Local builds display `UI: dev`. To embed a release tag, use
`flutter build web --dart-define=UI_VERSION=v1.2.3`. The release workflow embeds
the Git tag before packaging the web image, so deployments using `latest` also
show the original release tag. The API version is loaded once at startup from
`GET /api/v1/version`; an unavailable version never blocks sign-in or normal use.
